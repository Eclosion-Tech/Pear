**Status: S0–S2b2c8 and reuse review merged; contiguous composition working branch, October 28, 2026.** The [composition boundary](PROTECTED_MAIL_COMPOSITION.md) connects bounded internal read/MIME custody to existing atomic ingestion and adds exact authenticated-owner retrieval of accepted results. ## Entry-point inventory

Every protected read needs an authenticated initiating principal and run, a current grant, an authoritative source revision and a recorded exposure. Every subsequent disclosure must satisfy all exposed sources and their parents. A source identifier, prompt warning, model citation, operation fingerprint or clean screening result grants no authority.

## Publisher and management trust boundary

The database publisher can read private backing tables through privileged HTTP SQL. Private tables and caller views cannot remove that platform authority. The publisher, trusted backup/restore services, host administrators and reviewed broker/importer are part of the trusted computing base. They must not project privileged results into an ordinary assistant's context.

The audited MCP registry and custom CRUD dispatcher query fixed structures; neither exposes arbitrary SQL selected by a model/API caller. Lifecycle does permit arbitrary `/sql`, but forwards the caller's token instead of upgrading it to publisher. A caller with a publisher token is therefore materially different from an ordinary AI making a SQL request. A regex denylist in one wrapper would not protect the other protocol paths or revoke a raw publisher credential.

S1 tests must exercise ordinary token protocol access and existing publisher-backed application readers. They must also document that explicit trusted publisher access succeeds. These are separate expectations. Future governed runtimes require broker custody of privileged credentials and substrate authorization; S0 does not provide that custody.

## Implemented private storage, governed inputs and fixed admission

The [storage contract](PROTECTED_MAIL_STORAGE.md) documents private mail records, source-policy generations and exposure/derived provenance. Original mail records and exact instruction review have explicit owner views; derived records and policy history have no new read projection. These staging APIs are not connected to a runner, prompt builder or settings UI and do not certify sanitization. Local promotion and [fixed inference](PROTECTED_MAIL_INFERENCE.md) have separate admission contracts; inference releases bytes once to the bound broker and calls no provider.

The private collection binds an authenticated human owner to an existing paused connection. A record binds its immutable external-mail source and collection; a receipt binds both the supplied event key and a server-derived mailbox UID tuple to that record. Staging accepts bounded typed literal text and a trusted importer sanitization declaration, without executable components, arbitrary source JSON or caller-supplied authority. Actual mailbox authenticity, sanitization and admission remain later adapter gates.

**Protected source metadata and restrictions are never ordinary page properties. Protected mail titles, bodies, summaries and RFC fields are never copied into ordinary page, component, property, snapshot, job, conversation, automation or notification fields.** A normal page ACL or prose warning cannot substitute for this storage boundary. Creating a collection writes no new page. The connection's pre-existing legacy root, label and sharing rules remain unchanged and are not relabeled protected.

Staging reducers derive ownership from the connection/collection, fix external-mail origin/revision, validate configured folder/direction and compute content digests from the committed representation. The sanitization version is an importer declaration, not a redaction certificate. Source identity, content and parent references are immutable. [governance.rs](../server/spacetimedb/src/mail/governance.rs) now stores explicit publisher-initialized ceilings, immutable history and current generations. Only exact owners or the publisher can narrow/revoke them; initialization cannot reset a later head. Current ceilings apply to every ancestor of a derived record. Missing policy denies processing, while existing human history remains readable. Initial ceilings are management configuration, never human approval or a grant.

Private contexts accumulate registered sources and inherited snapshots without removal. A frozen invocation supplies every parent of its derived output; model citations cannot replace that set. New writes recheck current ancestor policy, including revocation, even when using an older input snapshot. Source and exposure identifiers do not prove which bytes reached a model or authenticate a runtime. A future adapter must register all inputs before disclosure and block uncertain contexts; no existing prompt or model path does so yet.

Explicit caller-dependent views require authenticated human ownership, reject both AI identity representations and publisher identity, and provide no service/admin override. Content includes its exact source association. An owner using publisher identity receives no view rows; a separate owner channel is required. Trusted raw-table management access remains separate.

The [instruction contract](PROTECTED_MAIL_INSTRUCTIONS.md) adds immutable exact
revisions and owner approval/revocation decisions. Edits clear approval and keep
all known parents; publisher drafts copy a validated derivation's frozen body
and complete graph. Fresh manual roots have unknown provenance. Decisions prove
the authenticated owner credential, not physical human presence or display.
They do not initialize source policy, authorize processing or integrate with
ordinary mutable prompts. Trusted review UI/recipe, complete actual prompt/input instrumentation and external-operation admission remain required before runtime use. Local promotion separately checks the exact current instruction decision and frozen ancestry.

No native/MCP tool or custom CRUD mapping registers these reads. Owner views are excluded from broad worker subscriptions and `snapshot_tables_v2.json`; browser export hydration now uses only that policy's include list. Private backing tables are already outside generated public-table bindings and that policy's exact public-surface equality check. Keep them outside ordinary snapshot/import include lists. A dedicated protected export/restore path must preserve restrictions and invalidate old execution authority; it is not supplied by excluding the views.

The [S2a authority contract](PROTECTED_MAIL_AUTHORITY.md) adds explicit private
epoch enrollment, same-transaction invalidation on connection/key mutations and
terminal tombstones. Frozen processor revisions and retirement retain exact
configuration/credential-version declarations. These are not grants or
admissions. Future use must bind current owner/epoch/configuration, governed
instruction revisions, shared budgets and one-use admission. Controlled
server restart tests persistence only; crash recovery and external dispatch
remain separate gates. Ordinary restore also fences a processor-only workspace,
and active v2 import blocks new processor configuration.

S2b1 resolves exact immutable instruction revisions through the same source
graph. Explicit first policy enrollment is current-only, while already enrolled
historical retries remain inert. New edits retain prior enrolled instruction
sources and all known parents. These are data ceilings; missing policy denies
processing, and a current approved decision plus live restrictions must still
be checked independently in admission. Historical resolution is deliberately
available after edit/revoke/logout so lineage cannot disappear.

Source, record and receipt commit together. Exact replay is a no-op; changed content or another request key for the same mailbox event is refused. Ordinary v1/v2 restore rejects any retained collection even if all pages have been purged; collection creation and an active v2 session are mutually exclusive, while abort stays available. When protected runtime integration is added, local append, receipt and applicable checkpoint must consume their admission together. Do not wire the existing page-writing runner into the private schema before its authority and lifecycle design is ready.

Legacy mail pages remain legacy content. Do not relabel them protected or erase ambiguous historical sharing rules automatically. Protected connection migration must inventory existing destinations/grants, prevent the old runner from writing that connection, and leave recurring processing disabled until its release gate passes.

## S2 authoritative state placement

**Implemented for local promotion and fixed inference payload release; provider transport remains a gate:** keep live mail authority in the same SpacetimeDB module as protected source/storage state. S2a already retains connection epochs and immutable processor revisions here. Co-locate owner/connection state, connection epochs, monotonic processor-config revisions, source generations, workflow authority, per-run grants, shared root budget pools and operation admissions. PostgreSQL mirrors or cached snapshots cannot supply an atomic check against a concurrent SpacetimeDB pause, ACL change or source update.

The [local summary reducer](PROTECTED_MAIL_ADMISSION.md) validates the current owner/epoch/snapshot, bound service/run, exact current instruction approval, full stored ancestry and current source policies; computes the frozen append cost/hash; debits the shared grant pool; and inserts a unique private pointer/receipt in one transaction. It accepts no body/hash/byte-count/processor or cursor argument. The staged source itself remains an ancestor, so its later revocation still constrains future disclosure. Global once-per-stage identity excludes grants and runs; the separate request identity binds the original grant/run/nonce. A TypeScript `eligible` result and fingerprint authenticate nothing and reserve nothing. Concurrent child runs reference the same budget pool rather than independent copies.

Admission rows contain opaque references, fingerprints/digests, costs, epochs and bounded states, not message bodies, prompts or raw errors. Treat these identifiers as access-controlled security records rather than ordinary telemetry. Pause/resume and credential changes increment the connection epoch; provider/model/endpoint/key/backend changes increment the processor configuration revision.

The fixed inference procedure now implements a one-use `admitted` → `dispatching` transaction before returning the server-built request to its bound broker. Every retry denies payload release; the ledger retains references and commitments rather than another body copy. The provider transport must preserve that consumed state before external I/O. Revocation before that claim denies dispatch. After the dispatch claim, cancellation is best effort; the database transaction cannot encompass remote transmission. Preserve crash/unknown outcomes and spent budgets rather than resetting the admission for retry. Local promotion consumes its own admission atomically. The [connector checkpoint contract](PROTECTED_MAIL_CONNECTOR.md) separately verifies every already-stored S1 record before committing cursor/history/receipt together; it does not authorize the earlier read or import. The separate exact prepared-ingestion contract now supplies atomic storage/disposition/cursor linkage; bounded discovery is merged and sparse checkpoints are staged separately, while observation-bound body reads/ingestion and actual MIME/body integration remain later gates.

Preserve Cloud's PostgreSQL `mcp_answer_offers` ledger and device once markers for existing answer effects. Reuse its scoped store mechanics/interface where useful, without moving mail into that ledger, adding another approval path for the same answer effect or widening the human-frontend answer approval channel. There is no production PostgreSQL Sentinel adapter or live protected profile in this PR.
